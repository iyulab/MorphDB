# MorphDB Philosophy

> **"RDB의 강력함을 유지하면서, 접근 방식을 혁신한다"**

---

## 핵심 통찰: Virtual DOM for Database

### 문제 인식

관계형 데이터베이스(RDB)는 강력하다:
- **ACID 트랜잭션**: 데이터 무결성 보장
- **선언적 제약조건**: FK, UNIQUE, CHECK로 비즈니스 규칙 강제
- **최적화된 쿼리 엔진**: 수십 년간 검증된 성능
- **풍부한 생태계**: SQL, 인덱싱, 분석 도구

그러나 **직접 접근**의 대가가 있다:
- 스키마 변경 = 마이그레이션 지옥 (다운타임, 데이터 이동, 롤백 위험)
- 전문성 요구 = DBA 의존성, 학습 곡선
- 경직된 구조 = 애자일 개발과 충돌
- 보안 노출 = SQL Injection, 권한 관리 복잡성

### 해결책: 추상화 계층

**Virtual DOM**이 HTML DOM 직접 조작 문제를 해결한 것처럼,
**MorphDB**는 데이터베이스 직접 접근 문제를 해결한다.

```
┌─────────────────────────────────────────────────────────────┐
│  React/Vue 패러다임                                          │
│                                                             │
│  [개발자] → [Virtual DOM] → [Reconciler] → [Real DOM]       │
│                                                             │
│  • 선언적 UI 정의                                            │
│  • 변경 감지 및 최소 DOM 조작                                 │
│  • 복잡성 캡슐화                                              │
└─────────────────────────────────────────────────────────────┘
                              ↓ 동일한 원리 적용
┌─────────────────────────────────────────────────────────────┐
│  MorphDB 패러다임                                            │
│                                                             │
│  [개발자] → [Logical Schema] → [MorphDB] → [Physical DB]    │
│                                                             │
│  • 선언적 스키마 정의                                         │
│  • 논리적 변경 → 최소 물리적 변경                              │
│  • 복잡성 캡슐화                                              │
└─────────────────────────────────────────────────────────────┘
```

## 프로젝트 철학

### 1. 논리와 물리의 분리 (Logical-Physical Separation)

**원칙**: 사용자는 논리적 이름으로 작업하고, 물리적 구현은 시스템이 관리한다.

```
논리적 세계 (사용자 관점)          물리적 세계 (시스템 내부)
─────────────────────────         ─────────────────────────
customers                    →    tbl_a7f3b2c1
  └── email                  →      └── col_e9d8c7b6
  └── name                   →      └── col_f1g2h3i4
```

**효과**:
- 테이블/컬럼 이름 변경 = 메타데이터 업데이트만 (데이터 이동 없음)
- 물리적 최적화 = 논리적 인터페이스 불변
- 다운타임 제로 스키마 진화

### 2. 가상 제약조건 (Virtual Constraints)

**원칙**: 성능에 필수적인 것만 물리적으로, 나머지는 애플리케이션 계층에서 처리한다.

| 제약조건 | 물리적 | 가상 | 근거 |
|----------|:------:|:----:|------|
| Primary Key | ✅ | | 인덱스 필수, 조인 성능 |
| Index | ✅ | | 쿼리 성능 직결 |
| Foreign Key | | ✅ | 스키마 유연성 > 물리적 강제 |
| NOT NULL | | ✅ | 컬럼별 선택적 적용 가능 |
| UNIQUE | | ✅ | 조건부 유니크 지원 |
| CHECK | | ✅ | 복잡한 비즈니스 규칙 |
| DEFAULT | | ✅ | 컨텍스트 기반 동적 값 |

**효과**:
- 스키마 변경 시 FK 제약 때문에 순서 고민 불필요
- 마이그레이션 스크립트 단순화
- 런타임에 제약조건 활성화/비활성화 가능

### 3. 접근 차단은 기능이다 (Blocked Access as Feature)

**원칙**: 데이터베이스 직접 접근 불가는 단점이 아닌 **보안 기능**이다.

```
전통적 접근                        MorphDB 접근
─────────────────────────         ─────────────────────────
[App] ──SQL──→ [DB]               [App] ──API──→ [MorphDB] → [DB]
      ↑
[DBA] ──SQL──→ [DB]               직접 접근 경로 없음
      ↑                           모든 작업 = API 통과
[Tool]──SQL──→ [DB]               모든 작업 = 감사 가능
```

**효과**:
- SQL Injection 원천 차단 (SQL 자체가 외부에 없음)
- 모든 작업 감사 로그 자동화
- 권한 모델 단순화 (API Key 기반)
- 데이터 유출 경로 최소화

### 4. 복잡성 캡슐화 (Complexity Encapsulation)

**원칙**: 내부는 복잡해도 좋다. 외부 인터페이스만 단순하면 된다.

```
외부 (단순)                        내부 (복잡해도 됨)
─────────────────────────         ─────────────────────────
POST /api/schema/tables           • 해시 기반 물리 이름 생성
{                                 • 메타데이터 테이블 동기화
  "name": "customers",            • 동적 GraphQL 스키마 재생성
  "columns": [...]                • OData $metadata 갱신
}                                 • 실시간 구독 채널 생성
                                  • 감사 로그 기록
```

**효과**:
- 개발자 학습 곡선 최소화
- RDB 전문성 없이 RDB 파워 활용
- 내부 최적화 자유도 확보

## 역할 (Role)

### MorphDB가 하는 것

| 영역 | 역할 | 설명 |
|------|------|------|
| **스키마 관리** | 단일 진실 공급원 | 테이블, 컬럼, 관계의 정의와 진화 |
| **데이터 접근** | 통합 게이트웨이 | CRUD, 쿼리, 집계의 유일한 경로 |
| **제약조건 강제** | 가상 무결성 엔진 | FK, UNIQUE, CHECK 런타임 검증 |
| **보안** | 접근 제어 계층 | 인증, 인가, 감사, RLS |
| **실시간** | 변경 브로드캐스터 | WebSocket, Webhook 알림 |
| **호환성** | 다중 프로토콜 지원 | REST, GraphQL, OData |

### MorphDB가 하지 않는 것

| 영역 | 설명 | 대안 |
|------|------|------|
| **직접 SQL 실행** | 임의 SQL 쿼리 허용 안함 | 구조화된 쿼리 API 사용 |
| **데이터베이스 생성** | PostgreSQL 인스턴스 관리 안함 | 외부 프로비저닝 도구 |
| **백업 스토리지** | 백업 파일 장기 보관 안함 | S3, Azure Blob 연동 |
| **비즈니스 로직** | 저장 프로시저, 트리거 비권장 | 애플리케이션 계층에서 처리 |
| **BI/분석 쿼리** | 복잡한 분석 쿼리 최적화 안함 | 읽기 복제본 또는 데이터 웨어하우스 |

## 범위 (Scope)

### 핵심 경계

```
┌─────────────────────────────────────────────────────────────┐
│                    MorphDB 책임 범위                         │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  API 계층                                            │   │
│  │  • REST/GraphQL/OData 엔드포인트                     │   │
│  │  • 인증/인가 (API Key, JWT, SSO)                     │   │
│  │  • 요청 검증 및 변환                                  │   │
│  └─────────────────────────────────────────────────────┘   │
│                              │                              │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  추상화 계층                                          │   │
│  │  • 논리적 ↔ 물리적 이름 매핑                          │   │
│  │  • 가상 제약조건 검증                                 │   │
│  │  • 시스템 컬럼 관리 (_id, _created_at, ...)          │   │
│  │  • Write Pipeline (Transformer → Validator)          │   │
│  └─────────────────────────────────────────────────────┘   │
│                              │                              │
│  ┌─────────────────────────────────────────────────────┐   │
│  │  데이터 계층                                          │   │
│  │  • PostgreSQL 커넥션 관리                            │   │
│  │  • DDL/DML 실행                                      │   │
│  │  • 쿼리 빌딩 및 최적화                                │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
                              │
                    ┌─────────┴─────────┐
                    │   PostgreSQL      │  ← MorphDB 관리 대상
                    │   (런타임)         │     (프로비저닝 제외)
                    └───────────────────┘
```

### 포함 (In Scope)

- **스키마 생명주기**: 생성, 수정, 삭제, 버전 관리
- **데이터 작업**: CRUD, 필터링, 정렬, 페이지네이션, 집계
- **관계 관리**: 1:1, 1:N, N:M 관계 정의 및 JOIN 지원
- **보안**: API Key, JWT, RLS, 감사 로그, Rate Limiting
- **실시간**: SignalR WebSocket, PostgreSQL LISTEN/NOTIFY
- **대량 작업**: Bulk Import/Export (CSV, JSON, XLSX)
- **엔터프라이즈**: 조직 관리, SSO (OIDC), 백업/복원

### 제외 (Out of Scope)

- **인프라 프로비저닝**: PostgreSQL 설치, 클러스터 구성
- **고급 분석**: OLAP 쿼리, 데이터 과학 워크로드
- **애플리케이션 로직**: 비즈니스 규칙, 워크플로우 오케스트레이션
- **파일 스토리지**: 바이너리 대용량 파일 관리 (S3 연동 권장)
- **메시지 큐**: 이벤트 스트리밍, 복잡한 pub/sub (Kafka 연동 권장)

## 설계 지침 (Design Principles)

### DO (해야 할 것)

1. **모든 데이터 접근은 API를 통해서만**
   - 직접 DB 연결 경로 제공 금지
   - 디버깅용으로도 SQL 콘솔 제공하지 않음

2. **논리적 변경을 물리적 변경보다 선호**
   - 이름 변경 = 메타데이터 업데이트
   - 타입 변경 = 가능하면 가상 캐스팅

3. **물리적 최적화는 투명하게**
   - 인덱스 생성 = 백그라운드 자동화
   - 사용자는 "이 컬럼 검색 많이 함" 힌트만 제공

4. **모든 작업은 감사 가능해야**
   - 누가, 언제, 무엇을 했는지 기록
   - 민감 데이터 마스킹 자동화

5. **다운타임 제로 스키마 진화 목표**
   - 비파괴적 변경 우선
   - 파괴적 변경 시 명시적 확인 요구

### DON'T (하지 말아야 할 것)

1. **임의 SQL 실행 허용 금지**
   - SQL Injection 방지의 근본적 해결
   - 구조화된 쿼리 API로 대체

2. **데이터베이스 비밀번호 외부 노출 금지**
   - API Key만 외부 인터페이스
   - DB 자격증명은 서버 내부에만

3. **물리적 이름 외부 노출 금지**
   - `tbl_*`, `col_*` 해시명은 내부 구현
   - 사용자는 논리적 이름만 인식

4. **애플리케이션 로직 내재화 금지**
   - 저장 프로시저, 트리거 최소화
   - 로직은 애플리케이션 계층에

5. **단일 테넌트 최적화 금지**
   - 멀티테넌시 고려한 설계
   - 테넌트 격리는 기본 요구사항

## 핵심 가치 요약

| 가치 | 설명 | Trade-off |
|------|------|-----------|
| **안전성** | 직접 접근 차단 = 공격 표면 최소화 | 유연한 SQL 포기 |
| **유연성** | 논리적 변경 = 마이그레이션 최소화 | 물리적 최적화 직접 제어 포기 |
| **단순성** | API로 통일 = 학습 곡선 최소화 | 고급 DB 기능 일부 제한 |
| **감사성** | 모든 작업 기록 = 컴플라이언스 용이 | 성능 오버헤드 감수 |
| **확장성** | 멀티테넌시 기본 = 수평 확장 용이 | 단일 테넌트 최적화 포기 |

---

## 철학의 검증 질문

새로운 기능이나 변경을 고려할 때:

1. **"이것이 직접 DB 접근을 유도하는가?"** → Yes면 재고
2. **"논리적 변경으로 해결 가능한가?"** → Yes면 물리적 변경 피함
3. **"감사 로그에 기록 가능한가?"** → No면 설계 수정
4. **"멀티테넌트 환경에서 안전한가?"** → No면 구현 불가
5. **"API 사용자가 물리적 구현을 알아야 하는가?"** → Yes면 추상화 실패
