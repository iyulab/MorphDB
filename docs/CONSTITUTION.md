# MorphDB Constitution

> 이 프로젝트를 장기적으로 돌보는 모든 주체가 공유하는 철학·범위·품질 기준·개선 프로토콜.
> 일회성 작업 지시가 아니라, 판단이 갈릴 때 돌아오는 기준점이다.

---

## 1. 정체성과 철학

**MorphDB는 virtual-schema 레이어다.**

React의 Virtual DOM이 DOM 직접 조작 문제를 푼 것처럼, MorphDB는 **데이터베이스 직접 접근 문제**를 푼다.
개발자는 논리 스키마를 선언하고, 물리 스키마는 시스템이 관리한다.
런타임에 스키마를 바꿔도 마이그레이션 지옥이 없다.

### 전제: 사용자는 PostgreSQL을 직접 다루지 않는다

이것은 제약이 아니라 **설계의 출발점**이다.
직접 접근을 차단했기 때문에 MorphDB는 물리 스키마를 자유롭게 운용할 수 있고,
그 자유가 런타임 스키마 유연성의 원천이다.

| 원칙 | 내용 |
|---|---|
| **논리-물리 분리** | 사용자는 논리명으로 작업한다. 이름 변경은 메타데이터 갱신일 뿐 데이터 이동이 아니다. |
| **제약의 실제 경계** | **CHECK만 가상**(앱 계층 전용) — 표현식이 논리명 세계에 살아야 개명 유연성이 유지된다. PK·Index·FK·NOT NULL·UNIQUE·DEFAULT 는 **물리 강제**가 무결성의 최종 백스톱이고, 앱 계층 검증은 그 앞단에서 같은 규칙을 검사해 호출자 오류를 4xx 로 번역한다. 정합성이 유연성에 앞선다 — 논리-물리 분리의 유연성은 이름·구조에서 나오지, 무결성 제약의 포기에서 나오지 않는다. (2026-07-22 개정 — 종전 "PK·Index만 물리적" 선언은 구현과 어긋난 오기였다.) |
| **직접 SQL 차단 = 보안** | SQL 주입 불가, 전 접근의 감사 추적 가능. |
| **복잡성 캡슐화** | 단순한 API, 감춰진 내부. |

### 전제의 대가는 탈출구로 갚는다

사용자가 PostgreSQL을 직접 다루고 싶어진다면, 그 답은 **직접 접근을 열어주는 것이 아니라**
**정식 테이블명·컬럼명을 갖는 스키마와 데이터로 내보내기/가져오기를 제공하는 것**이다.

**virtual-schema 레이어는 편의여야지 감옥이어서는 안 된다.**
물리명이 난독화되어 있다는 사실이 사용자를 가두는 근거가 되는 순간, 이 설계는 정당성을 잃는다.
락인은 이 프로젝트의 가치가 아니다.

### 자기 정비 책임 (Self-maintenance)

일반 데이터베이스가 지시 없이도 인덱스를 최적화하고 죽은 튜플을 청소하듯,
**MorphDB는 virtual-schema 자체를 정리하고 최적화할 책임을 진다.**

이것은 선택적 부가 기능이 아니라 **레이어의 의무**다.
논리-물리 분리를 도입한 순간 물리 세계의 위생은 전적으로 MorphDB의 몫이 되었다 —
사용자는 그곳에 손댈 수 없기 때문이다.

여기에 속하는 일:

- 논리 객체가 사라진 뒤 남은 **물리 잔재**(고아 테이블·컬럼·인덱스) 청소
- 메타데이터와 물리 스키마의 **정합성 회복**
- 반복된 스키마 변경으로 누적된 물리 구조의 **재배치·압축**
- 사용되지 않는 인덱스·제약의 식별

**사용자가 청소를 요청해야 한다면 그것은 캡슐화의 실패다.**
정리는 조용히 일어나야 하고, 실패해도 데이터와 질의는 온전해야 한다.

### Hidden layer 원칙 (캡슐화의 집행 규칙)

목적을 달성하기 위해 시스템 스키마·시스템 테이블·물리 테이블명·내부 컬럼이 필요하다.
그러나 **API로 접근하는 사용자는 그것들의 존재를 알 필요가 없어야 한다.**

> **프로젝트(스키마 격리)가 존재하는 이유가 바로 이것이다.**
> 멀티테넌시 상품이 아니라, MorphDB가 물리 스키마를 자기 판단으로 운용하기 위한 **내부 운용 단위**다.
> 사용자가 PostgreSQL을 직접 다루지 않기 때문에 MorphDB가 스키마를 소유할 수 있다.

내부가 공개 계약으로 새는 순간 그것은 바꿀 수 없는 것이 되고,
virtual-schema 레이어는 자기 물리 구조에 묶인다 — 즉 **존재 이유를 잃는다.**

### 용도 중립성 (Use-agnostic)

**어떤 테이블이 올라가고 어떤 서비스가 쓰는지는 MorphDB의 관심사가 아니다.**
PostgreSQL이 자기 위에 무엇이 얹히는지 묻지 않듯, MorphDB도 묻지 않는다.

> **판별 규칙: "이 기능은 MorphDB가 어떤 용도로 쓰이는지를 가정하는가?"** → 그렇다면 거부.

### Non-goals — 명시적으로 하지 않는 것

> **이 목록은 예시이지 닫힌 목록이 아니다**(2026-08-04 개정). 판정은 §2의 테스트가 한다 —
> *"DB가 하는 일인가? 어떤 용도로 쓰이는지 가정하는가? 사람·조직·과금을 아는가?"*
> **목록과 테스트가 갈리면 테스트가 이긴다.** 기능명 목록은 성질이 다른 것을 이름이 겹친다는
> 이유로 과차단하고, 그러면 필요한 기능이 **이름을 바꿔 숨어든다** — 문서는 "없다"고 적힌 채
> 그것을 갖게 된다. 실제로 그런 적이 있다(구 인증의 키가 역할을 지니고 있었다).

- **SaaS 정체성** — 회원가입·조직·멤버십·초대·SSO·과금/쿼터·플랫폼 관리자. 전부 소비앱의 책임이다.
  **MorphDB는 사람을 모른다.**
- **시크릿과 역할은 Non-goal이 아니다**(2026-08-04 개정) — 직접 접속 경로를 차단했으므로
  DB의 user/pw 자리에 오는 것이 **시크릿(API 키)** 이다. N개를 발급하고 각각에 **역할**을 부여한다.
  시크릿은 사람이 아니라 **접속 주체**이며 이메일·초대·조직을 갖지 않는다.
  0.8.0에서 인증 기계를 걷어낸 것은 **개념이 틀려서가 아니라 집행되지 않는 경계를 광고했기
  때문**이다(프로덕션 발급 경로 부재 + 부트스트랩 순환). 복원은 그 두 원인을 없앤 형상으로만 한다.
- **운영 오케스트레이션** — 백업 생성·스케줄·보존정책·스토리지 타깃.
  `pg_dump`은 인프라 계층의 일이며, 그것을 제품 기능으로 감싸는 순간 MorphDB는 운영 도구가 된다.

## 2. 범위 경계

### MorphDB에 속하는 것 — "DB가 하는 일인가?"

스키마 정의·변경 · 데이터 CRUD · 질의와 집계 · 트랜잭션 · 뷰 · 인덱스 ·
행 수준 보안(RLS) · 계층 질의 · 대량 IO(batch/bulk/import/export) ·
변경 알림(webhook — LISTEN/NOTIFY의 HTTP 대응) · 감사 로그 · 진단(pg_stat_* 대응) ·
프로젝트(스키마 격리).

### MorphDB에 속하지 않는 것

"이 DB를 누가 어떤 제품으로 쓰는가"에 대한 가정:
조직 · 멤버십 · 초대 · SSO · 쿼터/과금 · 플랫폼 관리자 · 백업 오케스트레이션.

### 확장 문턱 — 2소비자 규칙

새 프리미티브를 추가하려면 **서로 독립적인 소비자 2곳 이상의 실측된 수요**가 필요하다.
1곳이면 소비앱에서 해결하고 수요가 모이길 기다린다.

### 소비자 다원성 원칙

**어떤 단일 소비앱도 MorphDB의 목적지가 아니다.**
Formbase도 마찬가지다 — 상류 소비자라는 이유로 Formbase의 요구가 MorphDB 방향을 결정하지 않는다.
인바운드 요청은 **"DB가 하는 일인가" → 2소비자 규칙** 순서로 통과해야 한다.

### 거부 판별 기준

- 소비자 도메인 개념의 주입.
- **범용어로 포장된 도메인 개념** — 일반적으로 들리는 이름에 도메인 의미가 숨어 들어오는 것도 같은 오염이다.
- "어차피 우리 소유라 바꾸기 쉽다"를 변경 정당화로 삼는 것.

### Formbase와의 경계

Formbase는 MorphDB 위에 **AI 레이어**를 얹는다.
경계는 양방향이다: 스키마 조작 기술은 MorphDB에 남고, 의미·온톨로지·`FormType`은 Formbase에 남는다.
**MorphDB는 자기 위에 온톨로지가 얹히는지 모른다** — 알면 용도 중립성이 깨진다.

## 3. 품질 기준

### 트레이드오프 충돌 시 우선순위

> **정합성 > 단순함 > 성능 > 편의**

아래일수록 먼저 포기한다.

### 설계 원칙

| 원칙 | 내용 |
|---|---|
| **사용자 문자열은 DDL로 직접 흐르지 않는다** | 기본값·CHECK 술어·인덱스 술어 등 사용자가 준 표현식이 DDL에 닿는 모든 지점은 **허용 목록이나 구조 검증**을 거친다. 검증 없는 경로는 그 자체로 취약점이다. |
| **Hidden layer 집행** | 물리 테이블명·시스템 스키마·내부 컬럼은 API 계약에 등장하지 않는다. 공개된 것은 바꿀 수 없는 것으로 취급한다. |
| **제약 경계를 명시** | 무엇이 물리적으로 강제되고 무엇이 앱 계층 책임인지 문서와 코드가 같은 말을 해야 한다. 사용자가 CHECK 를 물리 제약으로 오해하면(우회 경로 존재 가정) 데이터 정합성 사고가 난다. |
| **부트스트랩은 확장을 요구하지 않는다** | 관리형 PostgreSQL은 `CREATE EXTENSION`을 막는다. 내장 기능만으로 기동·프로비저닝이 성립해야 한다. |
| **경계 너머에서 침묵 금지** | 정확히 처리하거나 명시적으로 실패한다. 조용히 틀린 행을 반환하지 않는다. |

### 오류 처리

도메인 오류는 **오류 코드를 갖는 예외**로 표현하고, API 경계에서 적절한 상태 코드로 번역한다.
오류 코드는 공개 계약이므로 개명은 파괴적 변경이다.

### 검출력 기준 — "테스트가 있다"는 근거가 아니다

**핵심 보증**(데이터 손실·순서·동시성·DDL 안전·계약 경계)은
**"보증을 제거하면 red가 나는가"를 실측하고 근거를 남긴다.**

- **테스트가 프로덕션 코드를 호출하지 않고 같은 일을 다시 구현하면, 그 테스트는 자기 자신을 검증한다.**
  픽스처는 프로덕션 부트스트랩을 **복제하지 않고 호출한다.**
  이 조항은 실제 사고에서 나왔다 — 픽스처가 부트스트랩 DDL을 손으로 복제해 두어,
  프로덕션 DDL이 어떤 테스트에서도 실행되지 않은 채 결함이 초록 뒤에 숨었다.
- **패턴은 인스턴스가 하나가 아니다.** 결함 유형을 찾으면 같은 유형을 전수 조사한다.
- 테스트로 커버할 수 없는 불변식은 숨기지 않고 "논증으로만 유지, 미커버"라고 명시한다.

## 4. 개선 프로토콜

### 분류 체계

| 등급 | 정의 |
|---|---|
| **C1 · 정합성 위협** | 데이터 손실·순서·DDL 안전·계약 경계를 깨뜨릴 수 있는 것. 조용히 틀린 답을 반환하는 것 포함 |
| **C2 · 헌법 위반** | Non-goal 침범, 용도 가정 유입, hidden layer 누출 |
| **C3 · 기술부채** | 동작은 하나 구조가 결함을 가리거나 이중 정의를 만드는 것 |
| **C4 · 개선 기회** | 지금 문제는 아니나 더 정석적인 방법이 있는 것 |

### 문서 정책 — OSS `docs/`는 항상 정제된 상태를 유지한다

MorphDB는 공개 OSS다. 소비자가 `docs/`를 열었을 때 **무엇이 현재 사실인지**만 보여야 한다.

| 구분 | 위치 |
|---|---|
| **정제 문서** — 소비자를 위한 것 | `docs/` — API 레퍼런스, 아키텍처, 철학, 호환성, 테스트 가이드 |
| **개발 과정 문서** — 우리를 위한 것 | 엄브렐러 `claudedocs/morphdb/` — 로드맵, 계획, cycle-log, 이슈 초안, 리서치 |

- 개발 과정 문서는 **git 추적에서 제외한다.**
- **헌법이 non-goal로 규정한 방향을 가리키는 문서는 `docs/`에 남기지 않는다.**
  다음 기여자가 그것을 로드맵으로 읽는다.
- 문서에 개발 이력 메타데이터(`Status: Phase N`, `Author`, `Created`)를 남기지 않는다 —
  그것은 개발 과정의 흔적이다.

### 변경 크기별 승인 절차

| 구분 | 대상 |
|---|---|
| **자율 수행** | C3·C4, 문서 정제, 테스트 보강, 고아 정리 |
| **제안 후 진행** | C1·C2 수정, 새 공개 엔드포인트, API 계약 변경 |
| **반드시 논의** | Non-goal 경계 이동, 메이저 승격(**임의 금지**), **버전 범프** |

### 배포 규율 — push가 곧 공개다

> **MorphDB는 버전 범프를 push하면 nuget·ghcr로 즉시 자동 배포된다.**
> 되돌리려면 새 버전을 내는 수밖에 없다.

- 버전 범프 커밋은 **사람 승인 없이 push하지 않는다.**
- 릴리스는 `vX.Y.Z` 태그를 스스로 남겨야 한다. 태그 없는 릴리스는 하류가 핀할 수 없다.
- **고쳤다 ≠ 소비자에게 닿았다.** 수정은 배포 사슬의 마지막 칸까지 가야 완료다.

### 이슈 관리

이슈는 **초안 파일로만** 기록한다(엄브렐러 `claudedocs/morphdb/issues/`).
**GitHub에 직접 등록하지 않는다.** 등록은 사람이 결정한다.

## 6. 진화 방향

### 환영하는 장기 방향

1. **자기 정비의 자동화** — 고아 물리 객체 청소, 메타데이터-물리 정합성 회복, 누적된 구조의 재배치를
   스케줄·임계치로 스스로 수행한다. DB가 오토배큠을 돌리듯. **레이어의 의무이므로 우선순위가 높다.**
2. **런타임 스키마 진화의 심화** — 무중단 스키마 변경, 논리-물리 매핑의 재배치, 물리 최적화의 자동화.
3. **탈출구의 완성** — 정식 테이블명·컬럼명을 갖는 스키마·데이터 내보내기/가져오기.
   락인 없음을 증명하는 기능이며, 우선순위가 높다.
4. **질의 표현력** — 논리 계층에서 표현 가능한 것을 넓힌다(DB가 하는 일의 범위 안에서).
5. **다중 프로토콜의 일관성** — REST·GraphQL·OData·WebSocket이 같은 논리 스키마를 같은 의미로 노출한다.
6. **관측성** — 진단·감사가 "DB가 자기 상태를 말해주는" 수준으로.

### 명시적으로 가지 않는 곳

- SaaS 컨트롤플레인 (조직·멤버십·초대·SSO·과금/쿼터·플랫폼 관리자)
- 운영 오케스트레이션 (백업 스케줄·보존정책)
- SaaS 정체성 (회원가입·조직·멤버십·SSO·과금) — **시크릿·역할은 제외**(2026-08-04 개정)
- **메이저 버전 승격** — 0.X 유지. 승격은 팀 승인 후 수동으로만.

### 결정 기록

| 결정 | 내용 |
|---|---|
| virtual-schema 레이어 | 논리-물리 분리가 존재 이유다. 물리 구조가 공개 계약으로 새면 이유를 잃는다 |
| 사용자는 PostgreSQL을 직접 다루지 않는다 | 제약이 아니라 설계의 출발점. 프로젝트(스키마 격리)가 존재하는 이유 |
| 탈출구는 내보내기로 | 직접 접근을 열지 않는 대신 논리명 기반 export/import 를 제공한다. 락인은 가치가 아니다 |
| 자기 정비는 의무 | 물리 세계에 사용자가 손댈 수 없으므로 그 위생은 전적으로 MorphDB 책임이다. 청소를 요청하게 만들면 캡슐화의 실패다 |
| 제약 경계 (2026-07-22 개정) | CHECK 만 가상, 나머지(PK·Index·FK·NOT NULL·UNIQUE·DEFAULT)는 물리 — 정합성 > 유연성. 물리 FK 의 결과(참조당하는 테이블은 관계 해제 후 삭제, `TABLE_HAS_DEPENDENTS`)는 공개 계약 |
| 확장 의존 0 | 관리형 PostgreSQL에서 기동해야 하므로 `CREATE EXTENSION`을 쓰지 않는다 |
| 용도 중립성 | 어떤 서비스가 쓰는지 묻지 않는다. Formbase도 소비자 중 하나일 뿐이다 |
| **SaaS 표면 제거** (2026-07-20) | 조직·멤버십·초대·SSO·과금·플랫폼 관리자·백업을 제거한다. 용도 중립성 위반이다 |
| **시크릿·역할 채택** (2026-08-04) | 접근 경로가 API 뿐이므로 DB의 user/pw 자리에 시크릿이 온다. N개 발급 + 역할 부여. 거부 대상은 **SaaS 정체성**이지 접속 주체가 아니다 |
| **Non-goal 목록은 예시** (2026-08-04) | 판정은 테스트가 한다. 목록과 갈리면 테스트가 이긴다. 기능명 목록은 과차단하고, 과차단은 완곡어법을 부른다 |

## 7. 개정 절차

1. 개정 제안은 자율이다 — 단, 코드·현실 실측 근거가 필수다. 감사에서 같은 조항의
   헌법-현실 충돌이 반복 관측되면 개정 제안은 의무다.
2. 실측으로 어느 쪽이 옳은지 먼저 판정한다 — 헌법이 오기면 개정을 제안하고,
   현실이 결함이면 개선 프로토콜(§4)로 처리한다.
3. 확정은 메인테이너 승인으로만 한다.
4. 같은 사실을 말하는 문서 전체의 정합 반영까지가 개정이다. 개정된 조항에는 날짜를 남긴다.
   (선례: 2026-07-22 제약 경계 조항 개정 — 구현 실측이 헌법의 오기를 바로잡았고,
   CONSTITUTION·ARCHITECTURE·API·SYSTEM_COLUMNS·PHILOSOPHY 를 일괄 정합했다.)
